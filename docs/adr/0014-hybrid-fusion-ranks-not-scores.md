# 混合检索融合的是名次，而关键词路的名次沿用 009 的计数键

**状态**：accepted（P4 开工前拍板，2026-10-02）

`architecture §5.1` 的 as-built(P2-0009) 注 1 里写着"P4 的 RRF 会把分数重新变成次序本身"——
这句话在本次拍板时被订正：**RRF 的定义是名次的函数（`Σ 1/(k + rank_i)`，k=60），它不需要分数**，
而关键词路的名次继续用 009 那三个计数键 `(命中的不同词数 ↓, 命中列数 ↓, table_uid ↑)`，
`score_kw` 仍只做展示字段。

**为什么不改回 `score_kw`**：009 那次换键不是审美调整，是被真语料打穿的——68 列的
`product_stats_wide` 有 10 列注释都带"金额"，命中列数全场最高，把只对上"订单"+"金额"两个词、
5 列的 `order_main` 挤下了头名，roadmap §P2 验收 ① 当场破。而 `score_kw` 是"每词在 ILIKE 与
trgm 上取 max、再跨词求和"，宽表卡片正文里同族列名成一大堆，**按它排名次等于把那一刀重新插回来**。
被否掉的第三条路是"分模式"（`mode=keyword` 用计数键、`mode=hybrid` 用分数）：它让同一句话在不同
模式下的关键词名次不一样，验收 3 的 ef_search 单调性检查因此无法跨模式复用，调参诊断凭空多一个变量。

**后果**：① `mode='keyword'` 是"向量路整体下线"时的降级路径，它的行为与 P2 的 `LikeRetriever`
**逐字同构**，所以 009 的三条 live 用例继续是有效证据，不用重测。② `docs/architecture.md §5.1/§5.2`
两处字面要回写：§5.2 主流程那句"全局 top-80 → 权限过滤"与同节踩坑 ④"过滤要在 SQL 里做"自相矛盾，
统一成后者（权限过滤进向量 SQL，`datasource_id = ANY(可见源)`，粒度到源不到表——见 ADR-0008）；
§5.2 (3) 的 RRF 那句补上"两路名次各自的来源"。③ `chat_messages.retrieved` 里 012 留成 NULL 的
`score_vec/fused` 两格开始写**名次**而不是相似度，字段名不改（改名会牵动 §2.7 的列定义与前端契约）。
